# Мой трекер материалов

## Подробное техническое задание для Codex

## 1. Назначение проекта

Создай персональный сайт для планирования и отслеживания готовности учебных материалов по русскому языку. Это не техническая админ-панель, а основное рабочее пространство владельца: здесь пользователь выбирает тему, меняет статусы, запускает фокус-сессии, видит прогресс и получает игровые награды.

Пользователь работает нелинейно: может сегодня писать конспект одной темы, завтра делать интерактив для другой, затем вернуться к доске или домашнему заданию третьей темы. Сайт не должен навязывать строгий порядок работы.

Основная цель сайта — сделать процесс подготовки материалов наглядным, приятным и мотивирующим, не превращая продуктивность в давление.

## 2. Технологические ограничения

- Статический сайт, совместимый с GitHub Pages.
- Без собственного сервера, npm, сборщиков и постоянно работающего Node.js.
- HTML, CSS и JavaScript с ES-модулями.
- Firebase SDK подключается через CDN.
- Firebase Authentication используется для входа владельца.
- Cloud Firestore используется для постоянных данных.
- `localStorage` используется только для временного состояния активной фокус-сессии и локальных настроек интерфейса.
- Публичная часть работает без входа и доступна только для чтения.
- Личная часть доступна после авторизации.
- Интерфейс должен быть адаптивным и работоспособным в актуальных версиях Chrome, Edge, Firefox и Safari.
- Не использовать тяжёлые библиотеки анимаций без явной необходимости.

## 2.1. Обязательное исследование перед разработкой

Перед созданием сайта и перед каждым крупным этапом разработки изучи в интернете актуальные лучшие практики и удачные идеи для подобных продуктов.

Исследуй:

- современные Focus Tool и focus timer;
- персональные трекеры продуктивности;
- геймификацию рабочих задач;
- системы наград без токсичной продуктивности;
- интерфейсы профиля и истории активности;
- визуализацию ежедневной эффективности;
- доступные модальные окна, выпадающие списки, уведомления и кнопки-иконки;
- плавные интерфейсные анимации;
- требования `prefers-reduced-motion`;
- адаптивность подобных интерфейсов на небольших экранах.

Для технических решений используй преимущественно официальную документацию Firebase, MDN и спецификации веб-платформы. Для визуальных идей можно изучать качественные современные приложения и дизайн-паттерны, но не копировать чужой продукт целиком.

По итогам исследования перед реализацией:

1. Кратко перечисли найденные подходы, полезные именно для этого проекта.
2. Объясни, какие решения предлагаешь применить и почему.
3. Укажи возможные риски для производительности, доступности и удобства.
4. Не добавляй функции только потому, что они встречаются в других приложениях.
5. Не меняй утверждённую логику проекта без согласования с пользователем.

Если доступ к сети отсутствует, не останавливай работу: сообщи об этом и опирайся на устойчивые веб-практики и официальные знания, но не утверждай, что исследование в сети было выполнено.

## 3. Страницы сайта

### 3.1. Публичный трекер — `index.html`

Показывает:

- список тем;
- класс;
- пять видов материалов;
- их статусы;
- прогресс темы;
- поиск;
- фильтр по разделам;
- фильтр по статусам.

Публичный пользователь не может добавлять, редактировать и удалять данные. Профиль, монеты, история и фокус-сессии здесь не показываются.

### 3.2. Личное пространство — `tracker.html`

После входа пользователь получает доступ к:

- таблице тем;
- изменению статусов;
- добавлению, редактированию и удалению тем;
- созданию разделов;
- режиму «Фокус»;
- профилю;
- монетам;
- истории действий;
- эффективности за день.

Если пользователь не авторизован, показывается форма входа с полями «Логин» и «Пароль». Регистрацию на сайте не добавлять.

## 4. Модель учебных материалов

Каждая тема содержит:

- раздел;
- название темы;
- класс;
- статус конспекта темы;
- статус конспекта заданий;
- статус доски;
- статус интерактива;
- статус ДЗ.

В интерфейсе использовать слово «Тема». Если в существующей базе поле называется `rule`, не переименовывать его без отдельного задания и миграции.

Допустимые статусы:

- `План` — 0%;
- `В работе` — 50%;
- `Готово` — 100%.

Старое значение `Запланировано` при чтении считать равным `План`.

Прогресс темы — среднее арифметическое пяти статусов.

### 4.1. Управление темами

В личном пространстве должны работать:

- добавление темы;
- выбор существующего раздела;
- создание нового раздела;
- редактирование темы, раздела и класса;
- удаление темы только после подтверждения;
- немедленное обновление таблицы после сохранения;
- понятные сообщения об успехе и ошибке.

В таблице использовать обычную визуальную нумерацию видимых строк: `1, 2, 3...`. Она не хранится в базе и пересчитывается после поиска, фильтрации, добавления или удаления.

## 5. Визуальный стиль

Сайт должен выглядеть как современное, спокойное и приятное рабочее приложение. Главный визуальный ориентир уже находится в корне проекта:

```text
reference.png
```

Перед любыми изменениями интерфейса обязательно открой и изучи этот файл. Воспроизводи не отдельные пиксели, а его визуальную систему:

- атмосферу мягкого северного сияния;
- глубокий тёмно-синий и фиолетовый фон;
- мятные, голубые и лавандовые акценты;
- полупрозрачные стеклянные панели;
- тонкие светящиеся границы;
- мягкие цветовые переливы без резкого неона;
- спокойную взрослую геймификацию;
- компактную таблицу, режим «Фокус» и профиль как части одного цельного продукта.

`reference.png` показывает три состояния интерфейса рядом только для согласования дизайна. На рабочем сайте не нужно размещать эти три экрана одновременно. Реализуй их как реальные состояния и панели приложения.

Требования:

- тёмная сине-фиолетовая палитра с мягким северным сиянием в обычном режиме;
- более глубокая и спокойная версия той же палитры в режиме «Фокус»;
- аккуратные плашки;
- понятные кнопки с иконками и подсказками;
- достаточные внутренние отступы;
- заметные стрелки у выпадающих списков;
- плавные состояния наведения, нажатия, загрузки и сохранения;
- хорошая читаемость длинных названий тем;
- отсутствие визуального шума;
- поддержка клавиатуры и `aria-label` у кнопок-иконок;
- поддержка `prefers-reduced-motion`.

Дизайн не должен выглядеть как техническая админка, детское приложение или статичный рекламный баннер.

Качество интерфейса является одной из главных задач проекта. Нужен крайне приятный, цельный и аккуратный дизайн, которым хочется пользоваться каждый день.

Дополнительные требования:

- плашки должны иметь понятную визуальную иерархию и не сливаться друг с другом;
- основные и второстепенные действия должны различаться цветом, размером и контрастом;
- кнопки должны иметь понятные иконки, состояния наведения, нажатия, фокуса, загрузки и недоступности;
- у кнопок без видимого текста должны быть подсказки и `aria-label`;
- иконки должны быть выполнены в одном визуальном стиле;
- опасные действия, например удаление, должны визуально отличаться и требовать подтверждения;
- элементы управления не должны располагаться вплотную друг к другу;
- выпадающие списки должны иметь хорошо заметные стрелки и достаточный правый отступ;
- все кликабельные области должны быть достаточно крупными для мыши и сенсорного экрана;
- анимации появления, сохранения, раскрытия, начисления наград и перехода в режим «Фокус» должны быть плавными и согласованными;
- движение должно помогать понять изменение состояния, а не служить случайным украшением;
- анимации не должны задерживать действия пользователя или блокировать интерфейс;
- интерфейс должен сохранять читаемость при длинных названиях тем и большом количестве данных.

Перед масштабным визуальным изменением сначала подготовь краткое описание концепции или локальный прототип. Не переделывай сразу весь рабочий экран только по одной референсной картинке.

## 7. Режим «Фокус»

### 7.1. Запуск

В каждой строке темы есть компактная кнопка ▶ с подсказкой «Начать работу».

После нажатия пользователь выбирает один вид материала:

- Конспект темы;
- Конспект заданий;
- Доска;
- Интерактив;
- ДЗ.

После выбора запускается одна активная фокус-сессия. Одновременно нельзя запустить две сессии.

### 7.2. Активная сессия

Во время фокус-сессии показываются:

- название темы;
- выбранный вид материала;
- таймер в формате `ЧЧ:ММ:СС`;
- кнопка «Завершить»;
- кнопка «Отменить».

Активная сессия хранится в `localStorage`:

- Firestore Document ID темы;
- название темы;
- поле выбранного материала;
- понятное название материала;
- время начала.

После обновления страницы сессия восстанавливается, а таймер продолжает отсчёт по фактически прошедшему времени.

### 7.3. Живой дизайн режима «Фокус»

Режим не должен быть статичной иллюстрацией. Сам интерфейс должен переходить в состояние концентрации:

- фон страницы становится тёмным и спокойным;
- остальные темы приглушаются;
- активная тема выходит на передний план;
- рабочая область плавно раскрывается;
- по фону медленно проходят цветовые волны;
- фиолетовые, сиреневые, синие и мятные градиенты мягко перетекают;
- редкие световые частицы двигаются медленно и не отвлекают;
- возле таймера есть живой индикатор активной работы;
- при запуске и завершении используются плавные переходы.

### 7.4. Растущий анимированный кристалл

В фокус-режиме отображается один из четырёх подготовленных PNG. Ощущение живого объекта создаётся за счёт аккуратной CSS-анимации самого контейнера, свечения и плавной смены изображений.

Стадии роста:

| Фактическое время сессии | Файл |
|---|---|
| от старта до `09:59` | `assets/focus-crystals/crystal-05-min.png` |
| от `10:00` до `19:59` | `assets/focus-crystals/crystal-10-min.png` |
| от `20:00` до `29:59` | `assets/focus-crystals/crystal-20-min.png` |
| от `30:00` и далее | `assets/focus-crystals/crystal-30-min.png` |

В первые пять минут `crystal-05-min.png` можно показывать с немного меньшим масштабом и более спокойным свечением. На отметке `05:00` мягко усиливай его свечение, не меняя файл. Это сохраняет смысл стадии «5 минут» без создания пятого изображения.

Требования:

- стадии определяются фактически прошедшим временем;
- после обновления страницы восстанавливается правильная стадия;
- все PNG выводятся в одном контейнере одинакового размера с `object-fit: contain`, без скачков вёрстки;
- при смене стадии используй короткий crossfade и небольшое увеличение, а не резкий скачок;
- кристалл мягко пульсирует и слегка парит; цветовые переливы и ореол создаются CSS, исходные PNG не редактируются;
- при завершении происходит короткая приятная вспышка;
- при отмене свечение плавно гаснет;
- декоративный слой имеет `pointer-events: none` и не блокирует кнопки и события мыши;
- при `prefers-reduced-motion` показывается статичная текущая стадия.

### 7.5. Завершение сессии

После нажатия «Завершить» показать:

- длительность работы;
- текущий статус выбранного материала;
- варианты: оставить статус, поставить «В работе», поставить «Готово»;
- кнопку «Сохранить результат»;
- кнопку «Продолжить работу».

При продолжении таймер не сбрасывается. При успешном завершении сессия удаляется из `localStorage`, статус при необходимости сохраняется в Firestore, а прогресс темы пересчитывается.

Если сохранение не удалось, окно не закрывается, сессия не удаляется, пользователь получает понятную ошибку.

## 8. Профиль пользователя

В верхней части личного трекера расположен компактный блок профиля:

- имя;
- аватар или инициал;
- баланс монет;
- кнопка открытия профиля;
- кнопка выхода.

В открытом окне профиля показываются:

- текущий баланс;
- общее время в фокусе;
- количество завершённых сессий;
- количество выполненных задач;
- история действий.

### 8.1. История

История группируется по датам. Для каждой записи показывать:

- дату и время;
- тему;
- вид материала или название задачи;
- длительность фокус-сессии, если была;
- изменение статуса;
- сколько монет начислено;
- основание начисления.

Пример:

> 13 августа, 14:20 — завершена фокус-сессия «Конспект темы», 27 минут, +2 монеты.

История должна быть компактной, читаемой и поддерживать постепенную подгрузку при большом количестве записей.

## 9. Задачи

Добавь личный список рабочих задач. Задача может быть:

- связана с темой и конкретным видом материала;
- независимой пользовательской задачей.

Для задачи нужны:

- название;
- дата создания;
- дата выполнения;
- статус выполнения;
- необязательная связь с темой;
- необязательная связь с видом материала;
- кнопка запуска фокус-сессии;
- редактирование;
- удаление с подтверждением.

Завершение связанной задачи может предложить изменить статус материала, но не должно делать это без подтверждения пользователя.

### 9.1. Блок «Сегодняшние задачи»

На главном экране добавь компактный блок «Сегодняшние задачи». Он помогает пользователю выбрать, над чем работать именно сегодня, но не навязывает строгий порядок подготовки материалов.

Задача на сегодня создаётся из уже существующей темы и конкретного вида материала:

- конспект темы;
- конспект заданий;
- доска;
- интерактив;
- ДЗ.

Сценарий работы:

1. Пользователь открывает действия нужной темы.
2. Выбирает конкретный вид материала.
3. Нажимает действие «На сегодня».
4. Сайт автоматически создаёт документ в пользовательской коллекции `dailyTasks`.
5. Задача сразу появляется в блоке «Сегодняшние задачи».
6. Из задачи можно запустить фокус-сессию по соответствующей теме и виду материала.
7. Когда связанный материал получает статус «Готово», задача на сегодня автоматически отмечается выполненной.

В карточке задачи показывай:

- название темы;
- вид материала;
- отметку выполнения;
- кнопку запуска фокус-сессии;
- действие удаления задачи только из плана на сегодня.

Удаление задачи из блока «Сегодняшние задачи» не должно удалять тему и не должно менять статус материала.

Не создавай повторную активную задачу для одной и той же комбинации `materialDocumentId + materialField + date`. Если она уже добавлена на сегодня, покажи спокойное уведомление «Задача уже добавлена на сегодня».

Коллекцию `dailyTasks` не нужно создавать вручную в Firebase Console. Firestore создаст её автоматически при первой записи, которую выполнит сайт.

## 10. Монеты и геймификация

Монеты начисляются не за простое нажатие кнопки, а за подтверждённую работу.

### 10.1. Предлагаемый баланс

| Событие | Награда |
|---|---:|
| Выполнена обычная задача | +3 |
| Каждые полные 10 минут завершённой фокус-сессии | +1 |
| Максимум за время одной сессии | +6 |
| Быстрое продвижение статуса менее чем за 10 минут | +3 |
| Материал впервые получил статус «Готово» | +10 |
| Все пять материалов темы впервые готовы | +25 |

### 10.2. Быстрое достижение

Если сессия длилась меньше 10 минут, но статус продвинулся вперёд, показать достижение «Быстрый рывок» и начислить +3 монеты.

Продвижение вперёд:

- `План → В работе`;
- `План → Готово`;
- `В работе → Готово`.

Если статус не изменился или изменился назад, быстрый бонус не начисляется.

### 10.3. Защита от повторных наград

- Награда за готовность одного материала выдаётся один раз.
- Бонус за полностью готовую тему выдаётся один раз.
- «Быстрый рывок» для одного материала выдаётся один раз.
- Переключение `Готово → В работе → Готово` не создаёт новую награду.
- Каждое начисление имеет уникальный ключ события.
- Баланс и запись события сохраняются атомарно через транзакцию Firestore.
- Повторный клик, повторная отправка формы или обновление страницы не должны дублировать награду.

Материалы, которые уже были готовы до появления геймификации, не должны автоматически приносить монеты задним числом.

## 13. Эффективность за день

Показывать не оценку личности, а движение работы за текущий день.

Учитывать:

- выполненные задачи;
- минуты завершённых фокус-сессий;
- продвижение статусов;
- впервые готовые материалы;
- полностью готовые темы.

### 13.1. Прозрачная формула

Начислять баллы эффективности:

- выполненная задача: 10 баллов;
- каждые полные 10 минут фокуса: 4 балла, максимум 24 балла за день по этому компоненту;

- материал впервые готов: дополнительно 12 баллов;
- тема полностью готова: дополнительно 20 баллов.

Итог за день ограничить 100 баллами.

Показывать:

- числовое значение;
- прогресс-бар;
- короткое нейтральное пояснение;
- составляющие расчёта по нажатию.

Нулевой или низкий показатель не сопровождать осуждающими сообщениями. Время в фокусе учитывается даже без завершения материала.

## 14. Данные и Firestore

Рекомендуемые коллекции:

```text
materials/{materialId}
sections/{sectionId}
userProfiles/{uid}
userProfiles/{uid}/tasks/{taskId}
userProfiles/{uid}/dailyTasks/{dailyTaskId}
userProfiles/{uid}/focusSessions/{sessionId}
userProfiles/{uid}/rewardEvents/{eventId}
userProfiles/{uid}/dailyStats/{YYYY-MM-DD}
```

### 14.1. `userProfiles/{uid}`

```text
displayName: string
coins: number
totalFocusMinutes: number
focusSessionsCount: number
completedTasksCount: number
createdAt: timestamp
updatedAt: timestamp
soundEnabled: boolean
animationsEnabled: boolean
```

### 14.2. `tasks/{taskId}`

```text
title: string
materialDocumentId: string | null
materialField: string | null
completed: boolean
createdAt: timestamp
completedAt: timestamp | null
```

### 14.3. `dailyTasks/{dailyTaskId}`

```text
materialDocumentId: string
topicTitle: string
materialField: string
materialLabel: string
date: string                 // локальная дата в формате YYYY-MM-DD
completed: boolean
createdAt: timestamp
completedAt: timestamp | null
```

Документ хранится по пути `userProfiles/{uid}/dailyTasks/{dailyTaskId}`, поэтому отдельное поле `userId` внутри него не требуется. При чтении главного экрана загружай только документы с `date`, равной текущей локальной дате пользователя.

Для защиты от дублей используй детерминированный ID, составленный из даты, ID темы и имени поля, либо выполни эквивалентную проверку перед созданием.

### 14.4. `focusSessions/{sessionId}`

```text
materialDocumentId: string | null
topicTitle: string
materialField: string | null
materialLabel: string
startedAt: timestamp
endedAt: timestamp
durationSeconds: number
statusBefore: string
statusAfter: string
coinsAwarded: number
completed: boolean
```

### 14.5. `rewardEvents/{eventId}`

```text
eventKey: string
eventType: string
coins: number
materialDocumentId: string | null
materialField: string | null
taskId: string | null
sessionId: string | null
createdAt: timestamp
```

`eventKey` должен быть детерминированным и уникальным для неповторяемых наград.

### 14.6. Правила доступа

- `materials` и `sections`: публичное чтение; запись только разрешённым авторизованным пользователям.
- `userProfiles/{uid}` и все вложенные коллекции: чтение и запись только при `request.auth.uid == uid`.
- Публичный сайт не получает доступ к профилю, истории, задачам и монетам.
- Секретные ключи и пароли не хранить в репозитории или Firestore.

Правила Firestore подготавливать отдельным этапом и публиковать только после проверки.

## 15. Надёжность начислений

Для изменения баланса:

1. Сформировать уникальный `eventKey`.
2. Запустить Firestore-транзакцию.
3. Проверить отсутствие события с таким ключом.
4. Создать событие награды.
5. Увеличить баланс профиля.
6. Обновить связанную статистику.
7. Завершить транзакцию.

Не увеличивать баланс отдельно от записи события. История наград должна позволять восстановить и проверить баланс.

## 16. Этапы разработки

### Этап 1. Стабильная основа трекера

- публичное чтение;
- авторизация;
- статусы и прогресс;
- управление темами и разделами;
- поиск и фильтры.

Критерий: все операции сохраняются и переживают обновление страницы.

### Этап 2. Базовый Focus Tool

- запуск по теме и материалу;
- таймер;
- `localStorage`;
- завершение, продолжение и отмена;
- изменение статуса.

Критерий: обновление страницы не сбрасывает сессию, все кнопки работают.

### Этап 3. Живое оформление фокуса

- тёмный режим;
- волны и градиенты;
- анимированный кристалл;
- стадии роста;
- `prefers-reduced-motion`.

Критерий: меняется только оформление и декоративные элементы; обработчики кнопок и логика остаются рабочими.

### Этап 4. Профиль и правила Firestore

- профиль;
- отдельные пользовательские коллекции;
- безопасные правила;
- настройки звука и анимаций.

Критерий: один пользователь не может читать или менять профиль другого.

### Этап 5. Задачи

- создание, редактирование, выполнение и удаление;
- связь с темами;
- запуск фокуса из задачи.
- блок «Сегодняшние задачи»;
- действие «На сегодня» для выбранного вида материала;
- автоматическое создание документов в `dailyTasks`;
- автоматическое завершение дневной задачи при статусе материала «Готово»;
- защита от повторного добавления одной задачи на одну дату.

Критерий: задача сохраняется, выполнение не дублируется, а удаление из плана на сегодня не влияет на тему и её статус.

### Этап 6. История фокус-сессий

- сохранение завершённых сессий;
- группировка по дням;
- отображение в профиле.

Критерий: отменённые сессии не считаются завершёнными.

### Этап 7. Монеты и награды

- транзакции;
- уникальные события;
- быстрый рывок;
- готовый материал;
- готовая тема.

Критерий: повторные клики и смена статуса назад-вперёд не дублируют монеты.

### Этап 8. Уведомления и эффективность

- 30 случайных поощрений;
- уведомления о монетах;
- дневной показатель;
- разбор составляющих.

Критерий: уведомления не повторяются подряд и не блокируют интерфейс.

### Этап 9. Адаптивность и финальная проверка

- мобильная версия;
- клавиатура;
- доступность;
- разные браузеры;
- GitHub Pages.

## 17. Обязательный порядок работы Codex

Для каждого этапа:

1. Изучи текущий код и `git status`.
2. Создай резервный коммит до крупных изменений.

6. Проверь синтаксис JavaScript.

8. Проверь публичную и личную страницы.
9. Для авторизованных сценариев дай владельцу короткий чек-лист ручной проверки.
10. Не отправляй изменения на GitHub без прямого указания пользователя.
